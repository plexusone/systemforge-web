# v0.11.0 Release Notes

**Release Date:** 2026-11-25

The login page offers **Continue with email**, for SystemAuth's sign-in with a
one-time code mailed to the person. The code is entered on SystemAuth's own
page, so an application adds a button and nothing else: it never handles the
code.

| Package             | Version   |
| ------------------- | --------- |
| `@plexusone/auth`   | 0.3.1     |
| `@plexusone/pages`  | 0.4.0     |
| every other package | unchanged |

## Highlights

- **Email as a sign-in method.** `@plexusone/auth` adds the `SignInMethod`
  type, an OAuth provider or `email`, and uses it for `loginWithOAuth` and the
  BFF client's sign-in URL. The login page's `oauthProviders` accepts `email`,
  and the button goes to `/bff/auth/email`, which forwards `idp_hint=email` to
  SystemAuth.
- **Linking keeps its own type.** Linking an account is still by
  `OAuthProvider`, since an email address is not an account that can be linked.
- **A linked method the page does not know.** The linked accounts list shows
  the method's own name, such as `email`, instead of a blank one.

The release adds no breaking change: the new type only widens parameters, and
`@plexusone/auth` is a patch release so the `^0.3.0` ranges that the other
packages declare for it still hold.

## Requirements

SystemForge v0.37.0 or later for the button to work, with `social_login.email`
configured in SystemAuth. Deploy the server first: against a BFF that predates
`/bff/auth/email` the click answers `UNKNOWN_PROVIDER`, and against a SystemAuth
without email sign-in it lands on SystemAuth's own sign-in page. SystemForge
v0.38.0 or later asks a new account for its name, so the application receives
the name the person gave.

```tsx
<LoginPage oauthProviders={['github', 'google', 'email']} />
```

See [@plexusone/pages](../packages/pages.md) and SystemForge's
[Launching with Email Sign-In](https://plexusone.github.io/systemforge/guides/email-sign-in/).
